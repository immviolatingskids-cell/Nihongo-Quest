# Nihongo Quest v0.3 — Unified Learning Engine

## Pre-v0.3 architecture

Content lives in `src/data.js`; persistence is handled by `src/state.js`; `src/engine.js` owns mastery, review scheduling, XP, quests, curriculum and companion event emission; `src/app.js` renders screens and session controls. Before v0.3, question construction and answer comparison were embedded in `app.js`, while progress recording lived in separate engine functions.

The main fragmentation was at the question boundary: kana and vocabulary used different ad-hoc shapes, answer normalisation was local to the UI, and the UI decided when to call recorders. This made it difficult to inspect why an item was selected or to add another exercise type without touching multiple concerns.

## v0.3 architecture

The engine now exposes a shared internal contract:

```text
content item + session source
        ↓
createQuestion()
        ↓
question presentation
        ↓
evaluateAnswer(question, submitted)
        ↓
canonical answer result
        ↓
recordAnswerResult(result)
        ↓
progress / XP / quests / answer history
        ↓
Sakura learning event
```

`createQuestion()` produces a canonical question with `contentId`, `contentType`, `stage`, `prompt`, `expected`, accepted alternatives, input type, choices, audio target, source, and metadata. Existing specialised renderers still use their existing presentation fields; the canonical object is carried alongside them so grammar and conversation activities are not forced into vocabulary-shaped UI.

`evaluateAnswer()` is the authoritative comparison path. It uses explicit NFKC normalisation and removes presentation punctuation and whitespace without fuzzy matching. Its result includes correctness, submitted and expected values, matched alternative, content identity, stage, source, and question identity.

`recordAnswerResult()` is the shared progress boundary. It dispatches to the existing kana or vocabulary progress logic, preserving review scheduling, mastery, XP, quests and answer history. The UI's `session.answered` guard prevents duplicate submissions before the next question is rendered.

## Session composition

Existing builders remain intentionally small and reusable:

- Today's Journey balances weak items, due reviews, new vocabulary and kana.
- Smart Review selects due vocabulary and attaches its current skill stage.
- Mistake Practice selects weak vocabulary and kana confusion pairs.
- Focused practice selects a requested group or family.
- Curriculum lessons select the content declared by a curriculum node.

Items now carry a source reason such as `due review`, `recent mistake`, `new material`, `confusion pair`, or `focused practice`. The reason is preserved on the canonical question for future Focus Quest and adaptive-learning work.

`buildSession(mode, options)` is the shared dispatcher for Journey, Review, Mistakes, Focused Practice and Curriculum modes. `describeSession()` provides a compact developer-facing view of content ID, stage, source and mastery for generated sessions without adding technical noise to the learner UI.

## Progression and Sakura

Recognition, recall, listening and production remain the supported vocabulary ladder, with the existing skill-score and mastery calculations preserved. The engine emits `ANSWER_CORRECT` or `ANSWER_INCORRECT` after recording. Streak, lesson, session and milestone events remain behind the v0.2 companion boundary, with throttling and completion priority preserved.

## Persistence implications

The save schema remains compatible. A small storage abstraction makes the state module testable outside a browser while retaining `localStorage` in production. No existing saved fields were removed or renamed.

## Tests and verification

`npm test` covers explicit normalisation, Japanese input, accepted alternatives, structured result metadata, one-answer progress/XP integrity, one companion event, and session source metadata. `npm run build`, JavaScript syntax checks, and `git diff --check` were also run.

## Known limitations

Grammar and conversations still have specialised renderers and progress methods; they share the event/progress boundary but are not yet represented by the canonical vocabulary question model. Session resume persistence is prepared by the explicit session/question contract but the v0.4 resume UX is not implemented. The existing stage progression algorithm is preserved rather than redesigned into a full spaced-repetition system.

## Future extension points

New exercise types should implement a question adapter and answer-result mapping, then call the shared recording boundary. A future Focus Quest can compose the same source-tagged items with a time/length strategy, while adaptive learning can consume stage, mastery and source metadata without rewriting Sakura or XP logic.
